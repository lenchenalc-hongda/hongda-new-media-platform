# HongdaOS 商务单据档案 V2 — 分阶段实施（禁止提前上线）

## 已确认业务目标
每次业务员点击「归档并导出 PDF」，系统必须在网站内同时保留：
1. **PDF 原件字节**：保存到仅授权用户可读取的私有文件存储。
2. **完整报价数据**：包括客户、负责人、金额、条款、大项、每条明细和最终打印的语言。
3. **不可覆盖的版本**：同编号报价每次正式归档产生新的 Vn，保留旧 PDF/JSON。
4. **历史权限查询**：业务员仅可查询自己的报价档案；admin/manager 可查询本组织的报价；允许检索客户、编号、项目和时间。

## 当前 PR 范围（Stage A）
- 追加式 Supabase SQL migration，单独建立正式 quotation archive 表和私有 PDF bucket，不修改财务源表/客户池/RLS。
- API：报价提交时要求上传真实 PDF 二进制（base64传输；最高10MB），验证当前 Supabase session、active profile、报价必填项、PDF文件头、SHA256、私有文件存储成功后写入不可变的版本档案。任何一步失败都不报告「归档成功」。
- API：组织范围 + 负责人权限查询分页历史；单条档案快照和短期私有 PDF 签名下载（60 秒）。
- UI：历史报价搜索、版本号、金额、PDF下载、从旧报价生成新版。
- 不改变现有 PDF Header、金额计算、报价条款和浏览器打印。

## 上线硬门槛（Stage B，仍未完成）
当前浏览器 `window.print()` 无法获取用户实际保存的 PDF 字节。
不能在用户触发打印弹窗前就把 JSON 标记为「PDF 已归档」。
因此在更改「保存为 PDF」按钮前，必须提供并验收**自动 PDF 生成器**：
- 使用同一份 `DocumentPreview` HTML/CSS 渲染高保真的中文/英文 A4 PDF。
- 必须支持宋/黑/微软雅黑等中文字体、品牌抬头 PNG、红色总额栏、分页和 5 类工艺说明。
- 系统先生成最终 PDF 的 bytes，再一次性提交当前报价快照和 PDF 字节到 POST archives；返回 201 后由浏览器触发同一份 PDF 下载。
- 页面必须明确标示：正在生成、正在归档、归档成功 Vn、失败可重试；不能出现无 PDF 却显示成功。
- PDF 下载失败但服务端归档成功时提供「下载已归档原件」恢复入口，不要重复增加版本。
- 对同一用户单次提交加请求 idempotency key，重试不会导致双版本；需测并发。
- 浏览器打印入口如保留，应显式标为「本地打印（不归档）」。

**Stage B 尚未完成之前，本 PR 不得合并或申请 Production SQL。**

## 数据安全与部署前置条件
- 依照 AGENTS.md：不主动执行 Production SQL / RLS，也不自行 Merge。
- migration 必须先在 `hongda-review-dev` 等隔离测试项目执行；验证数据库关系、版本唯一、RLS、私有桶、权限测试。
- 仅 Production Supabase 项目需要独立审批迁移。上线先完成数据库迁移，再部署依赖这些表的新代码。
- 服务端仅在验证 session 和组织/owner 之后使用 service-role；密钥不得交给浏览器。
- 已归档版本不允许 UPDATE/DELETE API；后续修订必须新版本。
- 阶段一仅产品报价单，不包括机器合同正式归档。
- 历史搜索只返回 metadata，详情才返回完整快照，PDF 签名 URL 有效期 60 秒。
