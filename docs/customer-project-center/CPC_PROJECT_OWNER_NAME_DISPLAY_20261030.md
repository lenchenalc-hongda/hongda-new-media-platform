# HongdaOS CPC｜项目列表展示业务负责人姓名（2026-10-30）

## 需求

「客户项目 → 项目 → 全部」及其他项目列表筛选中，旧版只能显示「非我负责」，无法知道由哪位业务员负责，妨碍跨项目分工、沟通和管理。

**展示口径**：以项目权威负责人 `cpc_projects.owner_profile_id` 为唯一来源，并在同组织 `profiles.id` 对应 `full_name`。**不以项目创建人、客户池归属人、任务执行人或最近修改人代替**。客户池负责人和项目负责人并不必然相同。

## 用户界面

- 每个项目卡片标题旁直接显示 **「业务负责人：姓名」**。
- 当前登录用户是项目负责人时额外显示 **「（我）」**；其他项目不再仅显示模糊的「非我负责」。
- 「全部、我负责的、推进中、等待中、需要处理、已结束」共用一个项目卡片组件，保持现有筛选、排序及项目详情入口。
- 搜索框同时支持匹配业务员姓名。
- 当合法可见项目没有可读的姓名时显示 **「待确认」**，绝不推测或冒用客户归属人、创建人。
- 展示姓名属于只读功能，不修改员工档案、项目归属、销售提成、客户来源及业务状态。

## 为什么不直接开放 profiles 表

生产数据库原权限：普通销售仅可直接 SELECT 自己的 `profiles` 记录；管理员可管理档案，经理可读取组织内档案。直接在「全部项目」页面执行 `from('profiles').in('id',ownerIds)` 会导致**普通销售无法获取其他负责人姓名**。把整个 profiles 表授予销售读取会带来不必要的个人信息暴露，因此不可采用。

本次新增最小化只读数据库函数 `public.cpc_project_owner_names(p_project_ids uuid[])`，仅返回每个已允许访问的项目 `project_id` 和该项目负责人的 `owner_name`。该函数在 DB 内严格要求：
1. `auth.uid()` 对应有效的同组织管理员、经理或销售；
2. 项目属于当前组织，与负责人档案 `owner.org_id` 一致；
3. 该项目通过现有 `public.cpc_can_read_project(project.id,project.org_id)` 权限验证；
4. 单次输入项目 ID 数量上限 500；
5. 拒绝 `anon` 执行，且不返回个人邮箱、手机号、工资、员工 ID 等其他字段；
6. 原有 `profiles` 行级权限（RLS）不改动。

**发布必须先迁移数据库再合并前端。** 这是新增只读函数，不修改既有表列、RLS、历史客户或项目数据。

## 页面数据链

- `src/lib/customer-projects/server-reads.ts`：服务端首屏项目列表通过有权限的 Supabase 会话查询该 RPC；
- `src/app/api/customer-projects/projects/route.ts`：客户端获取项目列表时，同样通过该 RPC 读取，以免首屏和接口结果不一致；
- `src/lib/customer-projects/list-read-models.ts`：按照 `project_id` 映射项目的负责人姓名，保留现有 `ownerProfileId` 在服务端判断「我负责的」；
- `src/app/customer-projects/projects/ProjectsClient.tsx`：在所有筛选中展示名字，并允许搜索；API 不向浏览器暴露员工内部 profile ID。

## 已知生产数据与非生产验收

在检查时生产数据库共有 28 个项目，28 个都能匹配到非空负责人姓名（3 个不同负责人）。这不代表后续不会有人员离职或字段异常，所以继续保留「待确认」兜底。

已在独立 Dev 数据库执行只读 RPC 迁移并进行事务演练：跨角色、跨组织、项目读取权限、真实 owner 姓名一致性、匿名禁止访问及输入数量上限均通过；测试事务 ROLLBACK。不在 Production 创建虚构客户或项目，不扩散人员资料。

## 发布边界

本 PR 仅部署安全只读 RPC + 服务端/接口/客户端展示变更 + 回归测试。不得改动 R/P 客户评级、负责人分配规则、客户池来源、收入回款、薪资提成。需 CI 成功、Preview READY 和批准的精确 HEAD 才可进入正式上线，生产数据库迁移应先于网站部署。
