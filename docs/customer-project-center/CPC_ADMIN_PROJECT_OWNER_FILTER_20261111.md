# CPC 项目列表｜管理员按业务员筛选（2026-11-11）

## 需求与使用场景

管理员打开 **客户项目 → 项目 → 全部** 时，项目来自全组织、跨不同业务员，难以快速了解某位负责人的项目。

在现有六个项目状态 Tab 及关键词搜索**不变**的情况下，在「全部」Tab 的搜索框旁增加原生下拉选项：

- 默认 **全部业务员（项目总数）**，恢复查看全组织项目；
- 根据当前有可见项目的实际业务负责人，显示姓名及其项目数；
- 选择某人只显示此人负责的项目；
- 筛选与原有关键词搜索可以组合，显示「当前显示 N 个项目」；
- 选到其他 Tab 时自动重置业务员筛选，其他六种 Tab 行为不变；
- 负责人姓名缺失的项目仍在列表中，显示「姓名待确认」以便定位。
- 同名的不同员工应当成为**两个独立选项**，不能因名称相同混在一起。

## 数据、安全与技术

目前全部 CPC 项目已有权威业务负责人 `cpc_projects.owner_profile_id`，查询时依赖现有 Supabase 登录态的 RLS 和只读 `cpc_project_owner_names`，不能按客户创建人或项目建立人归属。

- 仅 role=`admin` 的用户，其服务端首屏数据和 GET 项目列表 API 会带上临时 `ownerFilterKey`；
- 对项目负责人 ID 进行排序后分配 `owner-1`、`owner-2` 等**页面内临时键**，不向浏览器暴露员工 UUID；
- 普通销售与经理不会收到筛选键，也不会出现管理员筛选框。现有项目可见权限不扩宽。
- 下拉值只影响**客户端展示**，没有数据库写入、RPC、RLS、存储结构或权限迁移；
- 数据仍依当前项目的权威 owner id，业务员姓名变更后显示更新；不同负责人重名不会合并；
- 下拉内容按当前可见项目动态生成，项目增减后无需配置名单。

## 验证与发布门槛

回归测试覆盖：
- 相同负责人多笔项目正确合并计数；
- 不同负责人即使同名也应当成为单独选项；
- 全部业务员和单个业务员筛选；
- 搜索框和六个现有 Tab 保留；
- 仅管理员生成筛选令牌；非管理员 API 和首屏不返回该值；
- 不返回 `ownerProfileId`，不改旧 RPC 和数据表。
